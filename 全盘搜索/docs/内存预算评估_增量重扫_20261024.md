# 「按顶层子目录增量重扫」内存预算评估

> 分析人：performance-analyst
> 方法：**解析真实 idx 二进制**（非估算）+ 用 MSVC 14.51 `/std:c++20 /O2 /MT` 在同机复现 `Vol`/`Rec`/`Res` 结构做实测。
> 所有数字均为 `GetProcessMemoryInfo().PrivateUsage`（= 任务管理器「提交/私有」）实测值。

---

## 0. 一句话结论

**只改「重扫粒度」不会让后台常驻内存变小**：在现有 monolithic `Vol` 上做增量合并，隐藏态必须持有 base（113MB），增量峰值 135–178MB，对比现状整卷 212MB 只降 16–36%，而隐藏态从 4.3MB 恶化到 113MB。要真正变小必须**换内存模型**：把 idx 改成 `mmap(PAGE_READONLY)` + 按变化域分片，实测**隐藏态常驻 2.0MB**、增量峰值 **15MB（典型热区）/ 66MB（最坏 C:\Windows）**、搜索全量扫描 25.5ms。

---

## 1. 实测基线（先纠正三个前提）

### 1.1 `sizeof(Rec)` = 48 B，不是 24 B

```
sizeof(Rec)=48  alignof(Rec)=8      <-- 实测
布局：5×uint32(20) + 4B pad + 2×uint64(16) + uint32(4) + uint8(1) + 3B pad
```
两个 `uint64_t`（size/mtime）把结构强制拉到 8 字节对齐，前 20 字节后补 4B，尾部补 3B。
→ **按 24B/文件估算会低估 2 倍**，这是本方案预算表里最容易错的一项。

其他实测常量：
| 项 | 值 |
|---|---|
| `sizeof(std::wstring)` | 32 B（x64，SSO 8 wchar） |
| `sizeof(std::string)` | 32 B |
| MSVC `vector`/`string` 增长因子 | **1.5×**（实测 cap/size 收敛到 1.5000） |

### 1.2 真实索引规模（从 idx 文件直接解析）

| | C: | D: | E: | F: |
|---|---|---|---|---|
| nRecs | **419,273** | 134,153 | 1,791 | 2,435 |
| nDirs | **102,970** | 19,780 | 118 | 102 |
| idx 文件 | 61.29 MB | 13.00 MB | 0.21 MB | 0.20 MB |
| nameBlob(UTF-8) | 16.17 MB | 3.16 MB | — | — |
| lowerBlob | 16.17 MB | 3.16 MB | — | — |
| 平均文件名 | 38.6 B UTF-8 | 23.6 B | — | — |
| 平均目录全路径 | **140.9 wchar** | 85.3 wchar | — | — |

**C+D 的 idx 合计 74.29 MB**（磁盘），而堆内是 113 MB —— 比值 1.52×，与 1.5× 增长因子完全吻合。

### 1.3 C: 索引 99.3MB 堆内存的真实构成（实测）

| 组成 | 大小 | 占比 |
|---|---|---|
| `recs`：419,273 × 48B × 1.11(cap) | 22.3 MB | 23% |
| `nameBlob` + `lowerBlob`：2 × 16.17MB × 1.5(cap) | 48.5 MB | 49% |
| `dirs`：102,970 × (32B wstring + 堆) | **33.1 MB** | **33%** |
| 合计 | **99.3 MB**（实测） | |

两个反直觉的点：
1. **`lowerBlob` 白白多花 16–24MB**：它是 `nameBlob` 的完整小写副本。中文/ASCII 混合路径下仅 `towlower` 的差异，可用「搜索时对小写匹配做逐字符 `towlower`」或「存一份 32-bit hash + 回查原串」替代，省 16–24MB。
2. **`dirs` 占 33%**：102,970 个目录存的是**完整绝对路径 wstring，每个都是独立堆分配**（实测 102,966/102,970 走堆）。而**每个目录本来就已有一条 `Rec` 存着自己的名字** → 全路径是冗余的。

### 1.4 现状整卷重扫峰值：真实 ~212MB，不是 200MB

```
base index resident (no reserve)   WS= 85.9MB  Private= 99.3MB   (C: only)
+ full C: rebuild in flight        WS=164.7MB  Private=196.2MB   [PEAK]
```
本机 C: 99.3MB，D:+E:+F: 约 +13.7MB → 全量索引 113MB（与实测 113MB 吻合，误差 <2%）。
整卷重扫峰值 = 113（旧索引常驻）+ 99.3（新 C: Vol）≈ **212MB**。
任务管理器读到的 200MB 是**扫描未完成时的采样**（那一刻新 Vol 的 capacity 还没涨到顶）。

### 1.5 一个此前没被算进去的项：结果集

```cpp
struct Res { std::wstring name, dir, sizeStr, timeStr; uint64_t size, mtime; uint8_t cat; };  // sizeof=152
...
it.dir = dd;                       // 每条结果复制一次完整父路径
done->items->push_back(std::move(it));
if (done->items->size() >= MAX_STORED) continue;   // MAX_STORED = 100000
```
实测 **1,149 B/条**（用 390-wchar 路径）。按真实平均 141 wchar 路径折算 ≈ **650 B/条**。
→ 一次宽泛关键词（如搜 `e`）打满 100,000 条上限时，**结果集单独就吃 57–65MB**。
可见态 113MB 是「索引已加载」的数，**没算宽泛搜索**；真实使用中 113 + 60 ≈ **170MB+**。

### 隐藏态：这是方案的致命点

```
=== D. hidden incremental (base must stay resident to merge) ===
```

## 3. 关键变量：子树规模 → 峰值内存的估算公式

### 3.1 单文件成本（实测锚点）

| 口径 | C:（avg 文件名 38.6B，dirs/rec=0.246） | D: |
|---|---|---|
| **堆内 Vol 常驻/临时** | **248 B/file**（不 reserve） | 156 B/file |
| 同上，`reserve()` 后 | 207 B/file | — |
| 磁盘 idx | 153 B/file | 102 B/file |
| mmap 后 | ~0 private | ~0 private |

### 3.2 公式

```
Peak_private ≈ Base_private + N_sub × C_file

C_file = 48×[1.1~1.5]                       // Rec（实测 48B，非 24B）
       + 2 × avgNameUTF8 × [1.0~1.5]        // nameBlob + lowerBlob

C: 盘代入：53~72 + 116 + 81  = 250~270 B/file   （实测 220~240，取上界 250 安全）
D: 盘代入：53~72 +  71 + 32  = 156~175 B/file
```

**速查（C: 盘，不 reserve，250 B/file）：**

| 2,000 | 0.5 MB | 113 MB |
| 10,000 | 2.5 MB | 116 MB |

| 50,000 | 12.5 MB | 126 MB |

| 160,000 | 40 MB | 153 MB |

**`C:\Windows` + `C:\Users` = 93.4% 的 C: 索引。**
也就是说：按「第一级子目录」切，**任意一个真实变更几乎必然落在这两个巨型子树里**，等于没切。降 16–36% 的账，是拿「隐藏态从 4.3MB 涨到 113MB」换来的。

→ **按目录树切是错的维度，应按「变化频率」切。** 见第 5 节。

## 4. Q3：隐藏态要合并就必须持有 base？—— 有办法避开

### 4.1 在现有 monolithic `Vol` 上合并的真实代价（风险 #1，容易被漏算）

`Vol` 是**扁平 `vector<Rec>` + 两个 blob + `vector<wstring> dirs`**，`Rec::parent` 是 `dirs` 的下标。
替换其中一个子树意味着：删除旧子树的 N_old 条记录 + 插入 N_new 条 → 后续所有 `parent` 下标和所有 `nameOff/lowerOff` 全部位移 → **必须整体重排（compaction）**。

| 步骤 | 常驻 |
|---|---|
| 旧 base | 113 MB |
| 新子树 Vol | 64.5 MB |
| 合并后的新 base（`CommitVol` 式整体替换） | 113 MB |
| **峰值合计** | **≈ 290 MB** |

**比现在整卷重扫的 212MB 更差。** 唯一能压住的写法是「原地 append + 墓碑标记」，但那样 `SearchThread` 的线性扫描要跳过墓碑、blob 只增不减，长期会单调膨胀。

### 4.2 四种避免 base 常驻的路子，按代价排序

| 方案 | 隐藏态 private | 增量峰值 | 代价 / 风险 |
|---|---|---|---|
| **A. 按子树分片成独立 `.idx`（推荐）** | **≈2 MB**（mmap，未触碰） | 只重建那一片：0.3–64.5 MB | 需改 `SaveVol/LoadVol/CommitVol/SearchThread`；分片数 ≈40。**重建一个分片 = 覆写该文件，根本不需要 base** |
| **B. monolithic idx + mmap 只读** | **2.0 MB（实测）** | 重建仍需整卷或整片在堆内 | 格式已 95% 可复用；改动最小、收益最大。但「改中间」仍需整体重写 61MB |
| **C. 只读按需加载（mmap + 不 preload）** | 2.0 MB | 同 B | 首次搜索 25.5ms soft fault（page cache 热）/ 冷盘 ~100–300ms |
| **D. 在堆内做增量合并（原方案）** | 113 MB | 135–290 MB | ❌ 不解决常驻问题 |

### 4.3 mmap 实测（这是本次评估最重要的数字）

直接映射真实的 4 个 idx（C+D+E+F，共 74.29MB），`CreateFileMappingW(PAGE_READONLY) + MapViewOfFile`：

```
after mapping all 4 (no touch)        WS=   6.7MB  Private=   2.0MB     <-- +0.2MB
total mapped bytes = 74.29 MB
cold-ish full scan of 74.3MB: 25.5 ms
after full scan (pages faulted in)    WS=  62.6MB  Private=   2.0MB     <-- private 一点没涨
after unmap + EmptyWorkingSet         WS=   0.1MB  Private=   1.8MB
```

**113MB private → 2.0MB private，56 倍。** 而且 WS 的 62.6MB 是 **file-backed、可随时裁剪**（`EmptyWorkingSet` 一拍即回 0.1MB，下次访问按需 soft fault）。
这正是 Task Manager「私有/提交」这个用户真正会看的数字想要的东西。

**格式改造成本极低**：磁盘上的 `RecP`(41B, packed) 已经是内存 `Rec`(48B) 的紧凑版，两个 blob 就是裸字节。`SearchThread` 直接扫 `RecP` 数组即可（x64 上非对齐 `uint64` 读只有极小代价），无需「反序列化进堆」。`LoadVol` 那 74MB 的 `ReadFile + U8() 转换 + push_back` 可以整个删掉。

## 5. Q4：CRT 堆碎片 —— 实测**不涨不回落**

5 轮「构建 C: 全量 Vol → 析构 → EmptyWorkingSet」：

```
round 1: built (no reserve)        WS= 114.5MB Private= 144.5MB
round 1: after delete              WS=   6.8MB Private=   1.9MB
round 1: after EmptyWorkingSet     WS=   0.1MB Private=   1.9MB
round 2: built (no reserve)        WS= 108.5MB Private= 144.9MB
round 2: after delete              WS=   0.6MB Private=   1.9MB
...
round 5: built (no reserve)        WS= 108.5MB Private= 145.3MB
round 5: after delete              WS=   0.6MB Private=   1.9MB
```

**结论：没有只涨不回落。** 5 轮后 private 精确回到 1.9MB，无 creep。原因：
- > 512KB 的大块（24MB 的 blob）走 VirtualAlloc 后端，`HeapFree` 即归还 OS；
- 小对象（`dirs` 的 wstring）走 LFH，同尺寸复用，不产生新区域。

### 但仍有两笔可测出的浪费

1. **`reserve()` 是最大单项收益**

| | no reserve | with reserve | 差 |
|---|---|---|---|
| base 常驻 | 99.3 MB | **82.8 MB** | −16.5 MB |
| 整卷重扫峰值 | 196.2 MB | **163.0 MB** | **−33 MB（−17%）** |

实测 `recs` cap/size = 1.113、blob cap 恰好 1.5×。建议在 `WalkVolume` 入口按「上一次该卷的记录数 × 1.2」预 reserve（数据从 idx header 的 `nRecs/nDirs` 直接可得）。

2. **`EmptyWorkingSet` 的边界**：它**只裁 working set，绝不动 private commit**。实测 delete 后 private 已自己回落到 1.9MB，EWS 只是把 WS 从 6.8 压到 0.1。
→ 现在隐藏态那 4.3MB private 是 CRT/DLL 底噪，**压不下去也不必压**；而 113MB 的索引 private，EWS 一丁点都帮不上。**别指望 EWS 救常驻内存。**

3. **构建后 `shrink_to_fit()`**：现状 WS 85.9 / Private 99.3 之间有 13.4MB「已提交未触碰」的 capacity 空洞。对两个 blob + recs 各做一次 `shrink_to_fit` 可回收约 13–17MB（一次性 ~10ms memcpy），稳态立省 ~15%。

## 6. Q5 明确结论与推荐阈值

### 6.1 「后台常驻内存会不会很大？」

| 前提 | 隐藏态常驻 | 可见/增量峰值 | 判定 |
|---|---|---|---|
| 只做「顶层子目录增量重扫」，不动 `Vol` 内存模型 | **113 MB** | 135–178 MB（差情况 290MB） | ❌ **依旧大，且比现在更差** |
| 同上，但分片按二级目录切（避开 Windows/Users 巨型片） | 113 MB | 118–153 MB | ⚠️ 峰值降了，常驻没救 |
| **mmap + 按变化域分片** | **2.0 MB** | **15 MB 典型 / 66 MB 最坏** | ✅ 小 |
| 再叠 `reserve` + `shrink_to_fit` + 去掉 `lowerBlob` + `dirs` 改紧凑 | 2.0 MB | 10–50 MB | ✅ 很小 |

### 6.2 推荐阈值

1. **单次增量重建的 private 预算上限 8MB** → `8MB / 250B = 32,000 文件`。
   超过 32k 文件的子树**不允许整体重建**，必须再细分一级。
   （本机会触发：`servicing` 155k、`WinSxS` 88.5k、`Users\Administrator` 104k、`AppData\Roaming` 43.9k、`Windows` 286k）
2. **分片必须按「变化域」切，不按目录树切**：
   - **冷区（62.7% / ~62MB）**：`Windows\servicing` + `WinSxS` + `System32` → mmap 只读，只在检测到 Windows Update（文件版本/`buildTime` 变化）时整体重建。
   - **热区（13.9% / ~14MB）**：`AppData`（58,408）+ `Desktop`/`Documents`/`Downloads` → 独立小分片，重建一次 13MB。
   - **温区**：`Program Files`、`ProgramData`、`Users` 其余部分 → 中低频重建。
3. **`RescanVolume` 的整卷路径应彻底取消**（现在 `SchedulerThread` 标记脏后仍走整卷 `WalkVolume`），改成「脏路径 → 映射到分片 → 只重建该分片」。
4. **`MAX_STORED = 100000` 偏高**：100k 结果 ≈ 57–65MB（`it.dir = dd` 每条复制一份完整路径）。建议降到 20,000（≈13MB）或把 `dir` 改成「父目录 id + 共享 `shared_ptr<Vol>`」，可降至 ~180 B/条。

### 6.3 风险清单

| # | 风险 | 说明 |
|---|---|---|
| 1 | **堆内增量合并会 2× base** | 扁平 `vector` + 偏移指针的结构，删中间记录必须整体重排。盲目实现会到 290MB。**必须分片或原地墓碑。** |
| 2 | **隐藏态收益全部作废** | 合并需 base → 113MB。`WM_CLOSE` 的释放逻辑与增量方案直接冲突，需重新设计（只有「重建完即落盘、之后不驻留」才成立）。 |
| 3 | **`dir` 悬垂** | 若改用 `string_view` 指向 `Vol::dirs`，`CommitVol` 原子替换快照 / `WM_CLOSE` 置空 `g_snap` 都会让在飞结果悬垂 → use-after-free。用「dir 下标 + 结果集持 `shared_ptr<Vol>`」而非裸 view。 |
| 4 | **顶层粒度几近无效（本机实测）** | `Windows`+`Users` = 93.4%。在别的机器上比例会变，但系统盘结构类似。 |
| 5 | **mmap 后搜索延迟** | 全量线性扫描 25.5ms（page cache 热）。冷启动首次搜索 ~100–300ms。需接受或加后台预热线程。 |
| 6 | **只测了 C:/D:** | E:/F: 是移动盘/小盘，样本不足；数据量大的机器上比例需重测。 |
| 7 | **建议 `reserve` 为独立先落地项** | 与增量方案解耦、零风险、−33MB 峰值，可立即做。 |

---

## 7. 落地顺序建议（按 收益/风险 排序）

1. **`reserve()` + 构建后 `shrink_to_fit()`** —— 零风险，整卷峰值 212→~180MB，稳态 113→~96MB。
2. **`mmap` 替换 `LoadVol`** —— 改动中等，常驻 113MB → **2MB**（本项收益是其他所有项之和的量级）。
3. **按变化域分片 + 只重建脏片** —— 增量峰值降到 15MB（热区）。
4. `dirs` 改「父下标 + 自名字偏移」（省 ~30MB）、`lowerBlob` 去掉或改 hash（省 ~16–24MB）、`MAX_STORED` 降档 / `Res::dir` 共享 —— 常数级瘦身。

> 附：全部实测程序与解析脚本在 `/tmp/mtest/`（`sz.cpp` / `frag.cpp` / `scen.cpp` / `mm.cpp` / `res.cpp`）与 `/tmp/parsec.py`、`/tmp/subtree.py`。可用 `build.ps1` 同款 MSVC 复跑。

# 补充：回应 architecture-analyst 的 5 个待验算点

## 补1. 稳态 113MB 的真实构成 —— 三方推算的偏差

| 项 | 架构侧推算（基于「64MB idx ≈ 90 万条」） | **实测** | 偏差原因 |

## 补3. 分片键该取几层 —— 这是本次最关键的数字，已测死

你的判断「第一级不够、要下钻」**方向正确**，但「下钻到 2–4 级」的表述会误导实现。实测两种算法结果差异巨大：

**算法 A：递归下钻直到每片 ≤ cap（错误做法）**
```
cap=25MB → C: 14,922 片，中位数只有 4 个文件/片，最大 104,265 文件
```
为什么爆炸：C: 有大量只含个位数文件的叶子目录（深达 5–6 级），逐个成片 → 上万个小文件。**文件数从 4 变 1.5 万，打开成本、NTFS 元数据、目录遍历全部恶化。**

**算法 B：只对超 cap 的桶下钻 + 把 < floor 的兄弟合并成一个 misc 片（推荐）**

| cap | floor | C: 片数 | C: 最大片 | D: 片数 | **两盘合计** | 片 key 深度分布 |
|---|---|---|---|---|---|---|
| 8 MB | 2 MB | 23 | 16.4 MB | 10 | **33** | {1:2, 2:3, 3:4, 4:7, 5:3, 6:4} |
| **25 MB** | **3 MB** | **11** | **24.9 MB** | **3** | **14** | {1:2, 2:5, 3:1, 4:1, 5:2} |
| 30 MB | 5 MB | 8 | 25.2 MB | 3 | **11** | {1:2, 2:2, 3:1, 4:1, 5:2} |

cap=25MB 时的实际分片（C:）：
```
Users\Administrator                        25 MB   ← 第一级不够，必须下钻
Windows\WinSxS                             21 MB
Windows\servicing\LCU\Package_for_...      20 MB
Windows\servicing\LCU\Package_for_...      16 MB
Windows                                     6 MB
Program Files                               5 MB
... 其余 5 片（tiny 兄弟已合并为 misc）
```

**定死的结论：**
- 分片键 = **变长目录前缀**（按 size 决定深度），**不是固定 2–4 级**，也不是固定 1 级。
- 目标 cap = **25MB**，floor = **3MB** → **全盘 14 个片文件**，最大 24.9MB。
- 你的「40–200 个片文件」高估了 **3–14 倍**。

# 补充三：分片构成 / exclusions / 一条实现约束

## 补14. 实现约束：分区是**构建期产物**，不是运行期函数

分片键表面看是「目录前缀」，但**前缀的深度是由 cap/floor 与当时的文件数算出来的**，因此它**不是路径的纯函数**——同一路径在不同时刻可能属于不同片。

因此必须写成：

> **分区只在全量重建时计算一次，结果物化进 manifest；增量更新路径只读 manifest，绝不重算分区。**

否则任何一次"某个目录文件数超过 floor → 触发下钻 → 片身份改变"，都会引起重排风暴。**manifest 是唯一提交点**，容量驱动的分区才是安全的。

## 补17. 一个能省掉整次重建的优化：父 misc 其实**不需要重建**

架构侧规则是「子片变空 ⇒ ①删子片 ②从父 exclusions 移除该前缀 ③**同一次提交重建父 misc 片**」。

**第 ③ 步可以去掉。** 论证：子片变空的含义是**该前缀下磁盘上已经没有文件了**（成功的全量重扫返回 0 条）。而父 misc 的当前内容 = 「父前缀下所有记录 − 已排除前缀」。被移除的前缀本来就没有记录，所以移除后父 misc 的记录集合**逐字节不变**，只有 manifest 里的 exclusion 列表变了。

代价对比（以 `C:/Windows` misc 为例）：

| 做法 | 内存 | 时间 |
|---|---|---|
| 重建父 misc（走完整个 `C:/Windows` 286,183 条再剪枝） | 5.5 MB | **≈ 5–7 s**（servicing 155k 单项就 4.0s） |
| **只改 manifest 的 exclusion 列表** | 0 | **≈ 0** |

**前置条件**：只有在子片**成功重建且返回 0 条**时才允许删 exclusion；重建失败/中断时必须保留，否则会静默丢路径。

## 补18. 可观测性建议
上述缺口之所以危险，是因为「路径被排除但子片不存在」这个状态无人发现。建议加一条启动自检：
- 对每个 misc 片，`manifest.exclusions` 里的每个前缀**必须**存在对应的子片文件；
- 反之每个子片的前缀必须出现在其父 misc 的 exclusions 里（或本身就是独立顶层片）。
不一致就强制全量重建该父前缀。这条检查成本 = 片数（14）× exclusions（≤3）= 极小。

| B) `Rec*` 强转 + 成员访问（依赖 SLAA / object lifetime） | 6.12 ms |
| 差 | **+0.01 ms（+0.1%，噪声）** |

**结论：合规路径零代价。** 建议：
- **不要为这个函数把全项目升到 `/std:c++latest`**（会牵动其他代码的稳定性），
- 读端统一用「`const uint8_t* base` + `memcpy` 取字段」的访问器，配 `static_assert(sizeof(Rec)==41 && alignof(Rec)==1)`。
- 若将来确实升 C++23，再换 `start_lifetime_as_array` 也不迟（接口可包在一个 inline 访问器里，调用点不用改）。

## 补35. 我自己刚踩到的一个坑，建议写进规约：所有 on-disk 结构都必须 `pack(1)` + `static_assert` 尺寸

我写对比基准时用了匿名 struct 解析头部却忘了 `#pragma pack(1)`：`IdxHead` 实际变成 48 B（8+4+**4pad**+8+4+**4pad**+8+8），`memcpy(&hd, b, sizeof hd)` 读 48 字节 → `nDirs` 取到垃圾值 → 目录循环跑飞 → **段错误**。

**建议规约**：每个磁盘结构体旁必须紧跟
```cpp
#pragma pack(push,1)
struct IdxHead { char magic[8]; uint32_t ver; uint64_t buildTime; uint32_t letter; uint64_t nRecs, nDirs; };
#pragma pack(pop)
static_assert(sizeof(IdxHead) == 40, "on-disk header must be 40B");
static_assert(sizeof(Rec) == 41 && alignof(Rec) == 1, "on-disk record must be 41B packed");
static_assert(sizeof(RecP) == 41);   // 若保留独立持久化结构
```
`static_assert` 是唯一能在编译期挡住"加字段忘记改 pack / 改 pack 忘记算尺寸"的手段。这类错误在运行期表现为**随机段错误或静默错读**，而不是编译错误。

# 补充七：⚠ 遍历耗时是「热后备池」值 —— 验收数字要改

## 补36. 我此前所有遍历耗时都取的是 best-of-N = 稳态值，不是首次值

连续 6 次遍历同一棵树（同一进程内，紧邻执行）：

**`C:/Windows/servicing`（155,412 文件 / 43,707 目录）**

| run | 耗时 | 相对 run1 |
|---|---|---|
| 1 | **4,411 ms** | — |
| 2 | 4,356 ms | −1.3% |
| 3 | 4,333 ms | −1.8% |
| 4 | 4,604 ms | +4.4% |
| 5 | 4,025 ms | −8.8% |
| 6 | 4,316 ms | −2.2% |

→ **几乎没有升温效应（±9% 噪声）**。原因：43,707 个目录的 NTFS 元数据工作集远超文件缓存，怎么跑都"不热"。

**`C:/Users/Administrator/AppData/Roaming`（43,890 文件 / 6,963 目录）**

| run | 耗时 | 相对 run1 |
|---|---|---|
| 1 | **584 ms** | — |
| 2 | 350 ms | **−40.1%** |
| 3 | 361 ms | −38.1% |
| 4 | 350 ms | −40.1% |
| 5 | 346 ms | −40.8% |
| 6 | 361 ms | −38.1% |

→ **首次遍历比稳态慢 40%**（584 → ~350 ms）。树小、目录少，元数据能进缓存，所以升温效应显著。

## 补37. 由此修正的验收数字

| 项 | 我之前报（稳态/best-of-N） | **应改为** |
|---|---|---|
| 最热片 `AppData\Roaming` 更新 | ~385 ms | **首次 ≤600 ms / 稳态 ~360 ms** |
| `AppData\Local\Temp` | ~40 ms | 首次 ~67 ms（按同比例外推）/ 稳态 ~40 ms |
| 冷片 servicing LCU（152,304 文件） | 3.5 s | **~4.3 s**（按 run1 的 35,229 files/s） |
| `C:/Windows` misc 剪枝后（23,165 文件） | 0.53 s | ~0.66 s |

## 补38. 结论：验收**不要**写冷盘绝对耗时，用运行期实测的占空比

架构侧的「每片记 `lastRebuildMs`，最小间隔 = `max(8s, 20 × lastRebuildMs)`」在这个数据下**恰好是正确解法**，因为：
- 同一台机器上重建耗时就能差 **40%**（缓存状态），写死阈值必然错；
- **真冷盘（重启后）还会更慢**，而 `lastRebuildMs` 是运行期实测、自动适应，天然免疫这个问题。

按实测值核对占空比（乘数 20 ⇒ 占空比 5%）：

| 片 | 实测重建 | `max(8s, 20×t)` | 占空比 |
|---|---|---|---|
| `Desktop` | 0.010–0.015 s | 8 s（floor） | 0.2% |
| `AppData\Roaming` | **0.584 s**（首次） | **11.7 s** | 5.0% |
| servicing LCU | **~4.4 s**（首次） | **88 s** | 5.0% |

> 架构侧示例里写的「385ms 热片 → 8s，行为不变」需要小改：按首次 584 ms 算是 **11.7 s**。策略本身正确，只是示例数字要换成首次值。

## 补39. 关于「P1a 后重测 DFS+subtreeEnd」：其实不必等 P1a

架构侧以为那组数（6.17 / 6.20 ms）是在合成数据上做的。**实际用的是真实索引 `snapC.idx`（419,600 条真实记录 + 真实 dirs + 从真实路径重建的目录树）**，只合成了两样东西：
1. 目录的 DFS 重排（`dirs` 的顺序）
2. `subtreeEnd` 数组

而这两样**都不影响结论**，因为：
- **热循环一个字节都不读 `dirs`** —— 这正是 subtreeEnd 设计的目的（补21：逐记录物化路径 76.6ms → 整数区间 0.02ms）；
- **`recs` 数组我完全没有重排**，只是把 `parent` 字段的值改写成 DFS 索引，所以 `recs` 的访存模式与真实文件**逐字节一致**；
- ver=2（48B）对热循环的影响已实测为 **+1.5% 噪声**（补20）。

→ **这组数可以直接用，不需要等 P1a。** 如果真的出现偏差，只可能来自 `dirs` 段的访存，而热循环不碰 `dirs`，所以不会有。

## 补40. 真冷启动首访延迟：需要重启机器，我不擅自做

`EmptyWorkingSet` 只能把页移到 standby list，造不出真冷盘（补19 已说明）。要测真实冷启动首访，**只能重启后第一次搜索**。
这个数决定「首搜 100–300ms 能不能写进验收」，但与 mmap 是否正确无关（mmap 本身已验证 private 2.0MB、扫描 9.6–41.4ms）。
**建议**：mmap 落地后，由团队在真实重启场景测一次；测量脚本可复用 `docs/bench/pf.cpp`（含 prefetch 与首访计时）。

# 补充八：用真实坏文件验证架构侧的「游标 == 文件长度」防线

## 补41. 防线 2 有效，且能抓住防线 1 抓不到的一类错误

架构侧加了「校验器走完整个结构后，游标必须精确等于文件长度」。我手上正好有一个**真实的坏文件**（`snapC48.idx`：生成时写成 44B stride，头部却声明 `ver=2` 即 48B），可以直接验证：

| 文件 | 声明 | 实际 | 防线1 `static_assert` | **防线2 游标校验** |
|---|---|---|---|---|
| `snapC.idx`（好） | ver=1 / 41B | 41B | 通过 | 游标 64,290,162 == 文件 64,290,162 → **接受** |
| `snapC_dfs.idx`（好） | ver=1 / 41B | 41B | 通过 | 游标 == 文件 → **接受** |
| **`snapC48.idx`（坏）** | **ver=2 / 48B** | **44B stride** | **通过（抓不到）** | **`nameBlob 越界` → 拒绝** |

**关键点：防线 1 抓不到这个错。** `static_assert(sizeof(Rec)==41)` 只检查**类型声明**，而这个错误在**文件内容**——结构声明是对的，文件写歪了。`static_assert` 看不见文件内容。

→ **两条防线是互补的，不是冗余**：
- 防线 1 挡「声明写错」（编译期，零成本）
- 防线 2 挡「文件内容与声明不符」（运行期，成本就是本来要走的那一遍遍历）

**这两类恰好是各自唯一能覆盖的**。架构侧把它定义成「把 idx 当不可信输入」是对的——一个后台常驻组件因为半截写入的 idx 而崩溃不可接受，而我这个坏文件正是「半截/写歪」的真实样本。

## 补42. 校验顺序建议（与我验证器实测一致）
1. `static_assert` 所有 on-disk 结构尺寸（编译期）
2. 读头 → 校验 magic/ver
3. **先用 `nRecs`/`nDirs` 做长度下界检查**（`sizeof hd + nDirs*2 + nRecs*recSize <= fileSize`），**再信任**这两个数
4. 有界游标逐段推进（dirs → recs → 8+nl → nameBlob → 8+ll → lowerBlob），**每步先查边界**
5. 游标必须 **精确等于** 文件长度
6. 任一步失败 → **该片无效 → 该卷全量重建**（不只重建该片，因为 manifest 与片可能同时不一致）

实现见 `docs/bench/verify.cpp`（含 `snapC48.idx` 这个真实反例）。
