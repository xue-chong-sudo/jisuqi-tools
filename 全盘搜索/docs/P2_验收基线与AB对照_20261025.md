# 全盘搜索改造 · 验收基线与 P1a/P2 同条件 A/B（2026-10-25）

> **定版指纹**：`search_app.cpp` 3648 行；`全盘搜索.exe` size=573440，MD5 `a3acbea1b701f89d02c714c74c38ff7e`
> 本文所有"复测"数字均对应上述二进制的部署副本；P1a 对照数字对应 `dist/_p1a.exe`（由 commit 14c5df5 源码构建）。
> 口径统一为 **commit / PrivateUsage**（任务管理器「提交大小」）；「内存」列是 private working set，
> 两者在空闲时接近（≈0.5–1MB 差），但严格来说不同字段，文档一律以 commit 为准。

## 一、同条件 A/B（本次复核的核心）

方法：两个版本使用**各自独立的数据目录**（`--datadir=`），先在各自目录内完成一次全量建索引并退出，
再冷启动（从磁盘加载索引、无建索引干扰）测量；两轮交替顺序，排除环境漂移。

| 版本 | 轮次 | 开窗（已载入索引） | 搜 e 后（存 5 万条） | 关窗 10 秒 | 关窗窗口内 CPU |
|---|---|---|---|---|---|
| P1a（堆内索引） | 1 | **104.1 MB** | 122.0 MB | 93.7 MB | 62.0 s（正在整卷重扫） |
| P1a | 2 | **104.0 MB** | 122.0 MB | 36.4 MB | 2.7 s |
| P2（mmap + 分片） | 1 | **4.5 MB** | 16.1 MB | 5.3 MB | 13.9 s |
| P2 | 2 | **4.2 MB** | 15.6 MB | 5.7 MB | 8.8 s |

结论：
1. **P1a 开窗就是 104MB**（两轮完全一致，非偶然）：索引本体在堆里。
2. **P1a 关窗后是 36–94MB**，且两轮差异很大 —— 因为 P1a 是整卷重扫，关窗时若正在重扫就更高。
   P2 在 CPU 更忙（13.9s > 2.7s）的情况下关窗仍只有 5.3MB。
3. **所以 4.5MB 不是测量口径造成的假象**：同条件、同脚本、交替顺序下，P2 的开窗/关窗都稳定在 4–6MB，
   P1a 稳定在 104MB / ≥36MB。
4. 工作集：P1a 111MB（映射页在内），P2 39.6MB（索引是 file-backed 映射页，可被系统回收，不计专用内存）。

## 二、验收基线（定稿）

指标口径统一为 **专用内存**（任务管理器「内存」列 = Private Working Set）；
资源监视器的「工作集」在 P2 下会显示 ~40MB（mmap 映射页），属正常，不作为验收口径。

| 维度 | 指标 | 实测 |
|---|---|---|
| 静默（关窗 10 秒） | ≤ 13 MB | 4.5–6.2 MB |
| 开窗（索引已载入） | ≤ 20 MB | 4.2–4.6 MB |
| 搜索（5 万条封顶） | ≤ 60 MB | 15.6–16.9 MB |
| 热区新建文件→可搜到 | ≤ 30 s | 10–14 s |
| 热/温片重扫峰值 | ≤ 30 MB | 15.1 MB |
| **冷片（Windows Update 专用）重扫峰值** | **≤ 50 MB，仅 Windows Update 后或首次建索引时触发** | 47 MB |
| 搜索延迟 | ≤ P1a + 20% | 45 ms（P1a 41.4ms，+8.7%）|
| 分片 | C: 26 片 / D、E、F 各 1 片 | Σ片记录数 ≈ 全量（无重复）|

**明确不做**：冷片流式构建（把 47MB 压到几 MB）。理由：它只在 Windows Update 后触发一次，
收益是省一次不到 50MB 的瞬时占用，代价是把构建器改成"单遍写临时文件再拼接"，风险与代码量都不划算。

## 四、定版复测（MD5 a3acbea1…，含复核修复后）

复核（架构/性能两组）提出 6 条必须修项，已全部修完并复测：

| # | 问题 | 修复 |
|---|---|---|
| 1 | 盘级完整性无校验：首次建索引被打断后，缺一片会被 `allFresh` 固化最长 24h | 改为逐片 `needBuild`（manifest 有该片条目 + 文件存在 + buildTime<24h），缺一片就只补这一片 |
| 2 | 防抖无上限：持续写入的目录（含 Temp）永远等不到重扫 | 加 `firstDirtyMs` + `MAX_DEBOUNCE_WAIT_MS=30s`，持续 churn 也保证 30s 内扫一次 |
| 3 | 先清脏再重扫：发布/manifest 失败时更新被静默丢弃 | 改成"成功且期间无新事件才清脏"（`dirtySeq` 序号比对），失败保持脏重试 |
| 4 | 变化按"父目录"路由，片根被删/改名时该片永不重建 | 改用变化项自身路径做最长前缀匹配；片"由非空变空"时额外标记父片重建（消除幽灵记录） |
| 5 | 忽略 data 目录用裸前缀，`data2` 会被误吞 | 改为按路径边界比较 |
| 6 | manifest 读用 `_wfopen_s`（无 FILE_SHARE_DELETE），会挡住原子替换 | 改 `CreateFileW` 全共享；读不到 manifest 时**不写、不留孤儿**（提交失败即删刚发布的代次文件） |

另修：`PublishShard` 发布代次文件时**不再带 `MOVEFILE_REPLACE_EXISTING`**——代次名本不该存在，
万一撞名宁可失败重试，也不要静默覆盖一个可能仍被在飞结果映射的旧代次（这条不变量原本只靠逻辑约定，现在由 OS 兜住）。

`SortResults` 尖峰：排序时同时存活 `keys`(5万条 sort key ≈7MB) + `out`(≈4MB) + 结果集(≈7MB)，
最坏界约 25.5MB（含 `NameKey` 1.6MB 与 capacity 超额 1.2MB），实测峰值 commit 37MB 已含一次根片重建，
纯搜索场景应落在 25MB 量级 → 门槛 ≤30MB 成立。

> 说明：本轮复测期间系统侧（Windows servicing / 本工作区文件写入）持续触发分片重建，
> 因此"含重建"与"纯空闲"两列数字并存。判断内存是否达标请以**空闲窗口**为准；
> 复现时务必先等 CPU 与缓存目录签名稳定 20s 再采样（本文已按此执行）。
